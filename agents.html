Use cases

One local policy engine. Four ways to use it.

Agents log in to apps all day. CookieGuard makes sure the session they get is worth trusting, wherever the login happens.

AI browser agents Browser Use

Add one audit to your Browser Use agent. CookieGuard reads the agent's browser over its own connection, sees both what the server declared and what the browser stored, and gates the next step on your policy. Works with any model; the demo needs no API key.

audit = CookieGuardAudit(allowed_origins=['http://127.0.0.1:3000'],
                        auth_cookies=['session_id'])
result = await audit.finish()
result.assert_policy()   # raises on FAIL or INCOMPLETE

Tests and CI Playwright · CLI · Action

How it works

The AI guesses. The rules decide.

Two layers on your own computer. The AI layer finds the "signed-in" cookie; the decision layer proves it and checks that it is safe. A guess never opens the gate.

Inside the AI layer

A lookup table for known cookie names, and a model for the rest: what it reads, how it was trained, how good it is.

Where the numbers come from

Nine short scenes: 20,000 real websites, the cookies they set, the site's own labels, a sealed test, and the privacy check. Press Play, or step through. Open full screen →

Inside the decision layer

Why a guess must never decide, and the three steps that turn it into a verdict.

INCOMPLETE is not a pass. If the expected cookie never appears, the observer disconnects, or an agent claims it logged in without doing so, CookieGuard returns exit code 2. In testing, an agent that falsely reported success still got INCOMPLETE.
Why it matters

How a stolen session happens

If a login cookie is stolen or misconfigured, an attacker can use the account without a password. Agents make it worse: they log in to many apps, fast, and nobody is watching the cookies.

🔓 Token exposure

Without HttpOnly, any script on the page can read the session cookie through an XSS flaw.

  • Script reads the token
  • Attacker is you instantly
  • No password needed
Caught by CG001 HttpOnly · CG002 Secure · CG012 tokens in web storage

🌐 Cross-site execution

Weak SameSite settings let another site trigger authenticated requests in your name.

  • Browser attaches the cookie
  • CSRF acts as you
  • Settings changed, money moved
Caught by CG003 SameSite outside policy

🎯 Domain scope and session reuse

A cookie scoped to the parent domain is shared with every subdomain. A session that survives logout stays usable.

  • One weak subdomain exposes all
  • Logout that doesn't log out
  • Guest session becomes the login
Caught by CG004 domain sharing · CG010 rotation · CG011 logout

Showcase

Campus Market: watch an agent get stopped

A fictional student marketplace, a real Chromium browser, the real local model and the real policy engine. Two stories, each with a broken server and a fixed one.

The shopping checkpoint

The agent finds a $42 calculator and signs in. Login works. The session cookie is missing HttpOnly, so CookieGuard returns FAIL · CG001 and checkout never opens: zero checkout requests, zero purchases.

The chat that stays private

Signing out should end access. In the broken version the old session is still accepted after logout: FAIL · CG011. Fix the server, run the same policy again: PASS. The table shows the local model's real prediction for every cookie, including its mistakes.

Every run uses real browser requests and real ONNX predictions. No LLM service, no API key, no payment endpoint; the task stops at order review. Cookie values are excluded from every report and the run evidence can be downloaded.

The showcase deliberately uses an opaque cookie name, cm, that name-based rules cannot classify. The model proposes it; the person confirms it; the policy and the session probes do the rest.

git clone https://github.com/aiscihub/cookieguard-ai
cd cookieguard-ai/examples/campus-market
npm ci --ignore-scripts
npx --no-install playwright install chromium
npm start        # open http://127.0.0.1:8767
